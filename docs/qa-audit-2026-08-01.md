## 1. 核心需求逐条核对（真假判定）

### R1 下单（单店）—— 部分真实
- ✅ 商品归属校验：`CreateOrderAction::buildLines` L40-42（商品不属于该商家 → 422）。
- ✅ 优惠券服务端计算，客户端 `coupon_discount` 不信（`CreateOrderRequest` 注释 L27-33）。
- ❌ **库存不扣减也不校验（假象）**：`persistItems` L61-74 只 `increment('sales')`，**从未 `decrement('stock')` 也从未 `stock >= qty` 校验**。Product 表有 `stock`/`flash_stock` 字段（`MerchantController::updateProduct` L204、`storeProduct` L228 都能写），但下单流程完全无视 → 任何商品（含 `flash_stock` 闪购）可被无限下单、可下负数/超量。这是功能级缺失，不是边界。
- ❌ **超长/溢出（未覆盖）**：`items.*.qty` 只有 `min:1` **无 `max`**（`CreateOrderRequest` L36）→ 可传 `qty=2147483647`，`qty*price` 超出 `decimal(14,2)` 上限 → DB 报错或静默截断。`items` 数组本身无数量上限。
- ❌ **下单幂等（未覆盖）**：`store` L27-87 无幂等键（Idempotency-Key）。客户端网络超时重试 → 同用户同购物车生成**重复订单**。

### R2 跨店合并单（旗舰差异点）—— 真实，但继承 R1 缺陷
- ✅ 父单 + 每店子单、`computeMerged` 单次配送费、每店独立结算：已实现且测试覆盖（`OrderControllerTest` storeMerged）。
- ❌ 同样不扣库存、同样无 `groups` 数量上限（`CreateMergedOrderRequest` L32 `groups` 只有 `min:1` 无 `max`）→ 可构造上千个 group 的巨型请求（请求体 DoS + 超大事务）。

### R3 支付（MoMo/ZaloPay/聚合）—— 验签真实，但"发起支付"是雷区
- ✅ IPN/回调 fail-closed 验签、金额必须等于订单额、extraData/orderId 绑定防掉包、Cache 重放防护：`PaymentController` momoIpn/zaloPayCallback/aggregatorCallback 全部到位（L93-287）。**这部分是真扎实的。**
- ❌❌ **双重扣款（假象+高危）**：`pay()` L37-84 每次都 `Payment::create([...])`，**不检查该订单是否已有 payment**；且 `payments` 表**无 `order_id` 唯一约束**（`2026_07_15_000800` L11-24）。机制：钱包单 `pay()` 后订单仍是 `pending_payment`（要等 IPN 才翻 `paid`，见 L27 状态门禁），用户**连点两次支付** → 2 条 Payment 行 + 2 次真实 MoMo 扣款；两条 trans_id 不同 → IPN 重放防护（按 trans_id）不拦截 → **客户被扣两次**。COD 因状态门禁安全，钱包单不安全。
- ❌❌ **超时 + 并发（假象）**：`pay()` 把 `$gateway->createPayment(...)`（L67，**发起真实 HTTP**）包在 `DB::transaction` 内。所有网关 HTTP 调用 `Http::post` **均无 `->timeout()`、无 try/catch**（`PaymentGatewayService` L70/226/360/436/452）。后果：①MoMo 慢/不可达时请求**永久挂起**（Guzzle 默认无超时）；②事务/连接被外部 IO 占用 → 高并发下**连接池耗尽 + 行锁堆积**；③网络异常直接抛 500，前端无友好提示。Sandbox 走 mock 不发真实请求，所以本地测试完全看不出。
- ❌ **第三方报错处理不一致（未覆盖）**：`createMoMo` 等业务失败（resultCode≠0）能优雅返回 `failed`（L85-88）；但**连接层异常（DNS/拒绝/超时）无 catch** → 裸 500。退款 `refund` 同样无超时（`PaymentGatewayService` L436/452），好在 `OrderController::cancel` 用 try/catch 兜住（L244），失败只标 `refund_error` 仍取消（可接受，但真实钱未退，依赖人工对账）。

### R4 取消 + 退款 —— 真实（依赖 R3 修复）
- ✅ `cancel` 仅对 pending_payment/paid/accepted 放行（L215）、合并父单级联子单（L220-224）、钱包单经网关退款（L230-233，已 Mock 测试）、COD 跳过（L230 条件）、骑手释放（L254-257）。逻辑完整。
- ⚠️ 上游 `refund` 无超时 → 取消接口在真实退款时可能挂起（见 R3）。

### R5 骑手接单/送达 —— 部分真实，并发有洞
- ✅ `accept` 有 409（自己 busy / 已被他人接）（L79-84）、状态门禁（L85）、送达 GPS 0.3km 校验（L116-127）、送达人必须是本人（L101）。
- ❌ **并发接单（未覆盖）**：`accept` 先读 `$order->rider_id`（L82）再 `update`（L88-93），**无 `SELECT ... FOR UPDATE` 或唯一/乐观锁**。两个骑手同时抢同一单：都读到 `rider_id=null` → 都通过 409 检查 → 都写入 → **一单两骑手**。Rider 表也无唯一约束防止。
- ⚠️ `nearby`（L18-41）仍返回**全部未分配+picked 订单，无半径上限**（架构审查已标记）→ 规模化下 PHP 逐单算距离 + 全量返回，性能/带宽风险。

### R6 结算 T+1 + 打款 —— 打款是"台账假象"
- ✅ T+1 按日聚合、仅 sub 单、排除 cancelled/refunded：`MerchantSettlementService` + `SettlementController::merchantIndex/confirmMerchant` 真实。
- ❌ **打款=手动台账（假象，已在前审标记）**：`adminPayout` L88-99 `MerchantPayout::updateOrCreate` 直接把状态写成 `'paid'` + `paid_at=now()`，但**没有任何银行/MoMo/ZaloPay 真实出款 API 调用**。即"已打款"只是数据库一行记录，钱根本没动。融资叙事里这是必须坦白的点。
- ⚠️ `amount` 可被管理员显式传 `0`（校验 `min:0` 允许 0）→ 标记"已付 ₫0"；且与 computed 无强制对账。

### R7 优惠券 —— 真实（含并发小洞）
- ✅ 服务端解析、`used_count` 递增（`CreateOrderAction::recordMerchantCoupon` L133）、`isValidFor` 校验有效期/门槛/用量（`Coupon` L52-73）、新人券每人每次首单一次性（`resolveNewUserCoupon` L157-181，靠 `CouponRedemption` 存在性判断）。**主体真实。**
- ❌ **优惠券并发超额（未覆盖）**：`isValidFor` 的 `used_count >= usage_limit` 检查（L70）与 `recordMerchantCoupon` 的 `increment`（L133）**非原子**。usage_limit=1 时两笔并发单都通过检查 → 都用掉 → 超额。新人券同理（`exists()` 检查后 `create`，L164-179 无锁）→ 同用户并发首单双补。属资金泄漏类。

### R8 鉴权 / 权限边界 —— 主体真实，1 处公开越权
- ✅ `register` 角色绝不取客户端、强制 customer（`AuthController` L72-91）；`login` 密码必验（L101-115）；`refresh` 轮换 + 失效判定（L127-153）；全部 Admin 路由 `ability:admin`（routes L104）；商家/骑手方法内归属 403；订单经 `OrderPolicy` 归属（本次重构已落地）。
- ❌ **商家入驻 `onboard` 是公开路由（越权/数据完整性）**：`routes/api.php` L68 把 `/merchant/onboard` 放在 `auth:sanctum` 分组**之外** → 匿名（无 token）也能调用；`MerchantController::onboard` L104-110 用 `$request->user()?->id`，匿名时写 `user_id=null` → **孤儿商家（无主商家记录）**。应至少要求 `auth:sanctum`。
- ⚠️ `POST /agents`（`routes` L35）也公开，需确认 Agent 是否允许公开注册（未查 AgentController，建议核实）。
- ⚠️ `login` 用户不存在返回 404（可枚举手机号），低危。

## 3. "看起来做了、其实是假象"清单（给老板/投资人的直白版）

1. **库存管理**：表有 `stock`/`flash_stock`，但下单不读不扣 → 等于没有库存系统。闪购能被刷爆。
2. **防止重复支付**：有 IPN 重放防护、有订单状态门禁，但只防"同一笔网关回调重复"，**不防"用户连点发起两笔支付"**。钱包单会被扣两次。
3. **支付可靠性**：IPN 收端很稳（fail-closed、验签、金额绑定），但**发起支付端**把外部 HTTP 塞进数据库事务且无超时 → 生产环境 MoMo 抖动时会拖垮整个下单链路。
4. **商家结算打款**：后台显示"已打款"，实际只是数据库一行 `status=paid`，**没有真的把钱打出去**。
5. **测试绿证**：`php artisan test` 能跑通，但只测了 happy path，**没测库存、没测双重支付、没测并发、没测超时** → 绿的是表面。
6. **新人补贴防刷**：有首单判定，但**并发首单能双补** → 补贴被薅。

## 4. 修复优先级建议（与融资路线图对齐）

- **P0（上线前必修，资金/数据完整性）**
  1. `pay()` 加幂等：同一订单已有 `success/pending` payment 则直接返回，不新建；`payments` 表加 `unique(order_id)`（+ 历史数据兜底）。
  2. 下单扣库存：`buildLines` 加 `stock >= qty` 校验，`persistItems` 用 `decrement('stock', qty)` 原子扣减（带 `where stock>=qty` 防超卖）。
  3. 网关 HTTP 调 `->timeout(10)` 且**移出 DB 事务**（先提交订单/支付行，再异步/带超时调网关；失败标记 pending 由前端轮询或队列重试）。
  4. `onboard` 加 `auth:sanctum` 中间件。
- **P1（并发/安全）**
  5. `accept` 用 `DB::transaction + SELECT FOR UPDATE` 或 `rider_id` 乐观锁防双接。
  6. 优惠券/新人券核销加行锁或 `UPDATE ... WHERE used_count < usage_limit` 原子更新。
  7. 加 `qty`/`groups`/`items` 数量上限校验。
  8. 下单幂等键（客户端 Idempotency-Key → 服务端去重）。
- **P2（融资叙事诚实化）**
  9. 结算打款明确标注"手动台账，真实出款 API 待接入（Phase1）"，勿在 BP 写成已自动化。
  10. 补并发/超时/双重支付的测试（用 Pest + Mock 网关），让绿证真正可信。
