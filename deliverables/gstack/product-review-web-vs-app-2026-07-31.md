## 3. 设计视角论证
- **C 消费者**：浏览/搜索/下单/跟单/支付，高频碎片化在途；依赖手机（GPS、推送、移动支付、相机扫码）；输入密度低（点选为主）→ App 天然契合，类美团 90%+ 订单来自 App，Web 仅作获客入口。
- **M 商家**：接单/打单/改菜单/库存/对账，营业时段持续、固定在柜台；设备=柜台 PC+打印机+键盘；输入密度高（菜单/价格/批量）→ Web 桌面端效率碾压 App，可加 App 仅做离店接单提醒。
- **R 骑手**：抢单/导航/拍照取证/联系顾客/看收益，高频户外移动；设备=仅手机（GPS、相机、蜂窝、电量）；输入密度极低（点按）→ 必须 App，Web 不可行。
- **L 管理**：商户审核/用户管理/数据看板/补贴配置，长会话办公室；大屏 PC、多窗口、键盘、数据表 → 必须 Web。

## 4. 市场视角论证（越南）
- **移动优先国**：智能手机渗透 ~70–80%，4G 普及、流量便宜，消费者与骑手几乎纯手机；Grab/Shopee/Zalo 等超级 App 塑造 App 习惯 → C/R 必做 App。
- **商家侧**：越南中小商户多在店用电脑经营，Web 后台符合既有工作流；店员不愿在共用设备装 App → M 重 Web。
- **PC/网页**：家庭 PC 拥有率低于手机，但商户与平台运营方有办公电脑；纯 Web 下单站对 C 端增量有限。
- **本地特色**：Zalo Mini App（H5 形态）在越南极普及，是 C 端获客高性价比 Web 替代渠道，建议复用招商落地页思路。

## 5. 落地路线图
1. **已规划/先做**：C App + R App（Capacitor 壳内 `mobile/`），打磨骑手 GPS/拍照/弱网离线。
2. **接着做**：L Web 管理后台（P1，运营必需）→ M Web 商家后台（P1，提效/留存）。
3. **后做**：C H5 获客页 + Zalo Mini App（P2）。

**落地形式**：复用现有 Laravel 11 API（Sanctum ability 已区分 `merchant|admin`），新建独立响应式 Web 前端（admin + merchant console），**不塞进 Capacitor 壳**；H5 复用现 `index.html` 招商落地页思路。

**工作量量级**：L Web ≈ 15–25 人日；M Web ≈ 20–35 人日；C H5 ≈ 8–12 人日；Zalo Mini App ≈ S–M。
